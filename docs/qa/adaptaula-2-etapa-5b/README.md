## 1. Prerrequisitos y separación de operaciones

Utilizar un proyecto Supabase de staging separado de producción, un despliegue Vercel preview/staging, dos cuentas **ficticias** A/B con buzones controlados para verificar recepción real, y un documento sintético sin datos de menores. Mantener en el gestor de secretos del entorno las claves de Supabase y las contraseñas de prueba; nunca en Git, capturas, informes ni argumentos de terminal. Apuntar `NEXT_PUBLIC_SITE_URL`, Site URL y Redirect URLs de Supabase al dominio **exacto** de staging. El navegador debe recibir solo la clave pública; la clave de servicio queda en servidor. No habilitar Stripe ni modelos reales: para el ensayo de integración del flujo de análisis usar `AI_MODEL_STANDARD=mock:default` únicamente en preview y etiquetar los resultados como simulados. La sonda PDF no llama a IA.

Separar tres pasos que requieren decisiones distintas:

1. **Inspección, solo lectura:** abrir `scripts/staging/inspect-schema.sql` en SQL Editor. Consultar `select to_regclass('supabase_migrations.schema_migrations') as cli_history;`; si devuelve un nombre, ejecutar además `inspect-migration-history.sql`. Guardar solo los identificadores PASS/FAIL y las versiones, sin filas de usuarios. Una historia ausente no demuestra que falten objetos; una fila 027 aplicada tampoco indica qué versión de su contenido se aplicó. Inspeccionar la firma y permisos de la RPC directamente.
2. **Migración, con autorización separada:** tomar copia de seguridad y comprobar qué 025–028 faltan. Si la antigua 027 ya consta como aplicada, **aplicar 028 compensatoria antes de desplegar la API nueva**; editar 027 en Git no cambia esa base. Si faltan 025–027, aplicar las pendientes en orden y 028 después. Revisar con el responsable las solicitudes de baja creadas en la ventana de la RPC vulnerable: su contraseña no está acreditada. No repetir migraciones a ciegas ni tocar suscripciones previas o Stripe.
3. **Validación:** repetir `inspect-schema.sql` (todas las filas PASS), probar con usuarios ficticios que `authenticated` no ejecuta ninguna firma ni inserta solicitudes y que B no ve datos de A. La suite `tests/rls-real` hace llamadas reales y crea/limpia usuarios: **solo fase B autorizada**, con `SUPABASE_TEST_CONFIRM` y un proyecto de pruebas desechable. Si falla la limpieza, conciliar sus objetos y usuarios manualmente antes de continuar.

Parar el despliegue si hay un FAIL, si 028 no ha cerrado la firma antigua, si el esquema no coincide con el commit, si el proyecto no está aislado o si no hay canal operativo para atender solicitudes de baja. Ocultar el control de solicitud mientras falte la migración o ese canal; el código ya lo oculta si falta la tabla, pero no puede detectar la ausencia del canal humano.

## 2. Auth y correo: recorrido con buzones ficticios

Verificar en el panel de Supabase el proveedor Email, la confirmación obligatoria, Site URL y las Redirect URLs de `/auth/callback` y `/reset-password` en staging. No usar los valores de producción. Con A: registrar → recibir realmente el correo → abrir el enlace una vez → iniciar sesión → cerrar sesión → recuperar contraseña por correo → abrir enlace → cambiarla → comprobar que la anterior ya no funciona y la nueva sí. Probar enlace caducado/reutilizado y sesión caducada: deben ofrecer reentrada sin mostrar contenido privado. Repetir acceso directo con B a un recurso de A: 404/denegación. Comprobar que la verificación de contraseña para la baja conserva la sesión principal. Si no llega un correo, registrar **pendiente/fallo**, no «Auth validado». La suite local de Auth y el simulador no prueban entrega de mensajes ni configuración de GoTrue.

## 3. PDF en Vercel: prioridad alta

Preparar una adaptación **ya entregada y sintética**, perteneciente al espacio personal de A, con tabla, figura, actividad y espacio de respuesta. La sonda no crea adaptaciones ni consume IA. Registrar privadamente el UUID, el número esperado de páginas físicas y textos inequívocos de la tabla y la actividad. El comparador local es `pnpm smoke:pdf`: usa el renderer de CLARO, Chromium de `@sparticuz/chromium`, prueba la ruta de descarga, fuentes Inter, figuras, A4, páginas y la traza de ficheros. Su resultado **no** valida Vercel.

Después de autorización, configurar **nombres** de variables `STAGING_BASE_URL`, `STAGING_ALLOWED_HOST`, `STAGING_TEST_EMAIL_A`, `STAGING_TEST_PASSWORD_A`, `STAGING_TEST_EMAIL_B`, `STAGING_TEST_PASSWORD_B`, `STAGING_ADAPTATION_ID`, `STAGING_EXPECT_PAGES` y `STAGING_EXPECT_TEXT` (marcadores separados por `|`) en el entorno seguro de ejecución. `STAGING_BROWSER_PATH` puede indicar Chromium local. Ejecutar `node scripts/staging/pdf-probe.mjs --authorized-staging`. Sin bandera o variables se niega a conectar. Exige HTTPS, host exacto, 401 anónimo, 200 de A, 404 de B, cabeceras privadas, PDF A4, páginas y texto sintético esperado; reporta duración, bytes, operaciones de imagen e ID de solicitud, **sin guardar ni imprimir el PDF**. Un marcador de texto no prueba que la figura esté completa: revisar visualmente el PDF con la ficha sintética de referencia, tabla, figura, espacios y fuentes. Comparar páginas, texto y disposición con el PDF local de la **misma** ficha. Si la ficha no está entregada, bloquear la sonda hasta preparar un fixture legítimo; no sustituirla por otro material ni usar una salida mock como evidencia del generador.

En Vercel registrar duración real, uso máximo de memoria disponible, errores de arranque/render/validación y el ID de solicitud. El código declara `maxDuration=60`; el motor usa Chromium serverless, `playwright-core` y fuentes locales. Confirmar el límite efectivo del plan Vercel, la inclusión del binario en el bundle y la descarga autenticada. Un build correcto no acredita que Chromium arranque allí. Si falla, detener despliegue y correlacionar el ID de la respuesta con logs técnicos sin registrar URL firmada, título, contenido o contraseña. No sustituir CLARO.

## 4. Storage, cuotas y privacidad

- **Storage:** con un PDF sintético subir por la aplicación, abrir vista privada y descargar original; guardar un borrador y descargar específicamente su revisión guardada, comprobando que original y versión generada no cambian. B y una sesión anónima deben recibir denegación. Para originales grandes, comprobar que la redirección firmada dura un minuto, no es pública permanente y deja de servir tras caducar; no publicar la URL en evidencias. Revisar en el panel que los buckets siguen privados y que el navegador no recibe rutas internas fuera de lo necesario. La suite `tests/rls-real` prueba políticas y firma contra Supabase real; no equivale a comprobar la ruta completa de la app.
- **Free:** crear dos workspaces ficticios. En A, verificar en BD y en Plan y cuenta 1 adaptación/2 análisis/2 perfiles/5 páginas, la segunda adaptación y el tercer análisis bloqueados, la caché sin nuevo consumo, un fallo definitivo que devuelve reserva una sola vez, y el periodo siguiente sin consumo anterior. B debe conservar su propia cuota. Estas operaciones requieren el preview con proveedor simulado y pueden crear jobs: solo fase B. Los tests locales `commercial-policy`, `free-plan-adaptations` y `materials` ya ejercitan estos contratos, pero los límites efectivos de staging se deben leer de su `plans` y `workspace_usage`, no inferirlos de Git. No modificar suscripciones existentes ni adelantar el reloj remoto.
- **Privacidad:** con A comprobar alcance del JSON y originales incrustados frente a archivos mayores por ruta privada, exclusión de contenido compartido y tercera descarga bloqueada. Con B, denegar copia de A. Una contraseña errónea no crea solicitud, la correcta la registra una vez, la llamada RPC directa falla y la cuenta sigue trabajando. Realizar la prueba de baja solo si existe canal de atención; después dejar la solicitud ficticia documentada para tramitación/limpieza. No marcarla como eliminación ejecutada.

## 5. Fallos y evidencias

Registrar por caso: `PASS`, `FAIL` o `NO EJECUTADO`; fecha UTC, commit, nombre del entorno, configuración **sin valores secretos**, ID de solicitud y código de error técnico, duración y memoria cuando aplique. No registrar documentos, transcripciones, nombres de menores, URLs firmadas, tokens ni contraseñas. En errores de Auth, Storage, PDF y cuotas, comprobar que el usuario recibe un mensaje útil y que el log contiene solo identificadores opacos y códigos. La ruta PDF añade `X-Request-ID` y duración/resultado a logs; no registra el detalle libre de errores de Chromium.

Ante cualquier fallo de seguridad (RLS, RPC, Storage, datos cruzados), detener la validación y no publicar el despliegue. Ante fallo de PDF, mantener el release anterior y conservar el ID para diagnóstico. Una migración ya aplicada no se revierte reescribiendo su fichero: preparar una compensatoria probada sobre copia de staging. Si una prueba creó objetos o cuentas, inventariarlos y limpiarlos mediante el procedimiento autorizado para ese entorno; no borrar datos de otros usuarios. La eliminación física de cuentas pertenece a otra etapa con política de conservación y proceso recuperable.
